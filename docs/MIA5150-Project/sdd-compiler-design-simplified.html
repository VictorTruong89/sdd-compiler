Design note

The Spec-Driven Development (SDD) Compiler

Atomize each specification as it is written, place it in a layered graph, and surface the conflict it creates while the author still remembers why they wrote it.

1

The idea, and the five painpoints it exists to answer

Spec-driven development lets a human describe a system in ordinary language. That is its whole advantage, and the source of every problem below.

1.1 What this is

Spec-driven development lets a person describe a system in normal but highly ambiguous vocabulary rather than in a strict, structured, skill-gated programming language. A specification written in English can be read by anyone, argued with by anyone, and changed without a compiler's permission.

The cost is that English has no type checker. Two specifications written three weeks apart can contradict each other completely and nothing anywhere will notice. The larger the spec set becomes, the less likely a human is to notice either — and the more expensive the eventual discovery.

The SDD compiler is a background process that watches a specification set the way make/CMake watches a source tree: it maintains a graph of the specification, knows what each change invalidates, and reports what no longer holds.

What it is not

⛔ This is not an attempt to turn SDD into a programming language.

1.2 The five painpoints

#PainpointWhy it resists a plain LLM prompt
★ P1 Consolidation and conflict resolution across spec sets. Module A has 5 atomic specs, module B has 5. Comparing them honestly is 25 pairwise judgments. Asked in one prompt, the model does not perform 25 comparisons — it performs an impression of them. Hallucination, positional bias and silently skipped pairs all follow. The pair count grows as n²; attention does not.
★ P2 The comparison is semantic, not structural. Two specs conflict by meaning, not by differing on a field. There is no key to join on. String matching cannot see it and embedding similarity actively misleads: a requirement and its negation are near-identical vectors. The judgment has to be an entailment decision made by a model.
P3 As-built code versus the full spec set. The same n² shape, with the ambiguity halved — code is unambiguous, the spec is not. Same explosion, same blocking problem. Half the ambiguity does not halve the pair count.
P4 Carrying a spec set forward across releases while keeping relationships and history intact. Requires versioned identity for every unit of specification, which prose files in git do not provide at the granularity that matters.
P5 Progressive checking during authoring — surface the conflict now, not at the end of the session. A conflict found five minutes after writing is a two-minute fix. The same conflict found across a finished spec set is an archaeology problem.

The design

A layered graph, an incremental insertion loop with a human in it, and an invalidation rule borrowed from make.

2.1 The insertion loop

The author writes one or two specs in ordinary prose and presses a button. Nothing runs while they type. Two deliberate exclusions define the interaction:

  • ★ No typing-time analysis. Checking on every keystroke is technically harder and interrupts the thought being written down. The button is the commit point.
  • ★ No spec recommendation. The SDD compiler does not suggest what to write next. It reports conflicts with what already exists. Suggestion is a different and much harder product, and it would compete with the author's own thinking at exactly the wrong moment.

2.2 The layers

Layers exist for human cognition — so the author can see where a statement sits and what it refines — and they do a second job the design depends on: the layer is the blocking key. Conflicts cluster within a layer and along refinement paths; they are rare between an unrelated business goal and an unrelated data model. That is what makes the candidate set small.

2.5 Invalidation

The make analogy was invoked for the graph. The more valuable half is the invalidation rule: when a target changes, which dependents become out of date? Translated here, insertion of node N into a graph of 200 raises two questions:

  1. Which existing nodes must be judged against N? Not all 200 — the blocking claim.
  2. ★ Which previously clean nodes are now stale? When N resolves a conflict, or changes a dependency, earlier verdicts stop being trustworthy.

The second question is what checked_against exists to answer, and it is the one almost nobody implements. It is also what the marginal cost of one new specification in §3.2 measures — without invalidation, every edit pays the full price of the whole set again.

The MIA 5150 project

The same engine, framed as a claim that can be tested rather than a tool that can be demonstrated.

3.1 The claim

The one-sentence test

We claim that an LLM asked to find conflicts across a specification set is substantially more accurate, more stable and cheaper per conflict found when the SDD compiler decomposes the problem for it, and we will show it by measuring conflict recall and precision, tokens per conflict found, and run-to-run stability against the same model working without the compiler on a labelled specification corpus, across a range of corpus sizes and two judge models.

Two sentences that decide how everything below is read

Category: novel application.

★ The subject under measurement is the LLM model improvement, not the SDD-compiler tool.

3.2 Three comparison scenarios, and what they isolate

The same model, the same corpus and the same question — which specifications in this set conflict? — asked three ways. The scenarios form a ladder: each step adds exactly one thing, so any difference in the numbers has one cause.

ScenarioHow the model is askedWhat the step adds
S1 · No compiler
current practice		 The whole specification set goes into one prompt: "find every conflict in these specifications." Nothing. This is what a person does today, and the baseline every number is measured against.
S2 · Decomposition only Specifications are atomized, then every pair is judged in its own separate call. No graph, no layers, no filtering. Decomposition. Isolates how much of the gain comes simply from asking one small question at a time rather than one large one.
★ S3 · Full compiler Atomize → place in the layered graph → generate candidate pairs → judge only those. The graph. Isolates whether structure preserves S2's accuracy while removing most of its cost.
Why three and not two

Two scenarios would confound two different effects. S1 → S2 answers "does breaking the problem up help the model at all?" and S2 → S3 answers "does the graph keep that help while cutting the bill?" If S3 beat S1 in a two-scenario study, there would be no way to say whether the graph mattered or whether any decomposition would have done. The middle rung is what makes the contribution attributable.

Metrics — three families

Accuracy answers did the model find the right conflicts; cost answers what did that cost in tokens; stability answers would it say the same thing tomorrow. A tool that scores well on the first two and badly on the third is not usable, which is why the third family is not optional.

FamilyMetricDefinitionWhy it is in the table
A · Accuracy ★ Conflict recall true conflicts reported ÷ true conflicts present The headline. A missed conflict is the failure the whole tool exists to prevent.
Conflict precision true conflicts reported ÷ all conflicts reported A tool that raises false alarms gets switched off. Precision is what keeps recall honest.
F1 harmonic mean of the two One number for the summary row, never reported alone.
★ Recall by conflict kind recall computed separately for contradiction · duplication · subsumption · ambiguity Where the interesting result lives. Flat contradictions are easy for every scenario; subsumption is where a single long prompt is expected to collapse.
B · Cost Input / output tokens counted per run, reported separately They behave very differently: S1 is one enormous input, S2 is many small ones. Summing them hides the mechanism.
★ Tokens per true conflict found total tokens ÷ true conflicts recovered The efficiency number that cannot be gamed. A cheap run that finds nothing scores badly, which a raw token count would not show.
Judgments issued model calls per run — 1 for S1, n(n−1)/2 for S2, |candidates| for S3 The compiler's direct effect, before any accuracy question.
★ Marginal cost of one new specification tokens to check node N against a graph already holding n nodes The incremental claim. S1 and S2 pay their full price again on every edit; S3 should pay only for the candidates. Measured as a curve, not a point.
C · Stability ★ Run-to-run agreement Jaccard similarity of the conflict sets across k repeats at fixed settings Same prompt, same model, different answer. Expected to be worst in S1, and it is rarely measured anywhere.
Order sensitivity agreement across shuffled specification order (S1, S2) or insertion order (S3) Positional bias, stated as a number. If a result depends on the order things were written, it is not a result.
Judge agreement agreement between the hosted and local models on the same pairs Says whether the scaffolding substitutes for model capability, and on which conflict kinds it does not.

★ The scaling curve — the result worth building the study around

How to measure, in one paragraph

Run all three scenarios at corpus sizes of roughly 10, 25, 50, 100 and the full set, and plot recall against corpus size for each. The expected shape is the whole argument: S1 degrades as the set grows — one prompt cannot hold more comparisons than the model can attend to — while S2 and S3 stay flat, because each judgment is the same small question no matter how large the corpus becomes. A single table cell at one corpus size cannot show that. A curve can, and a degradation curve is a far stronger finding than a difference in means.

Measurement discipline

  • Count tokens, do not estimate them. Read the usage field the API returns; for the local model, count with its own tokenizer. An estimate in a cost table is a guess in a table of measurements.
  • Fix the decoding settings for the main table and record them with the seeds. The stability family then re-runs at those same settings — variance at fixed settings is the finding, so it must not be confounded with a settings change.
  • Report n beside every figure. A recall of 0.80 over five true conflicts is not a measurement.
  • Decide the headline metric before running anything. Choosing it afterwards, once the numbers are visible, is how an honest study becomes a dishonest one.
  • One corpus, three scenarios, no other differences. Same specifications, same labels, same judge model within a comparison. Everything that is not the scenario is held constant.

3.3 Eligibility — is this a foundation-models project?

The brief admits any topic "as long as it works with generative models or foundation models." Nothing in this project trains, fine-tunes or modifies a model, so the question deserves a direct answer rather than an assumption. Three lines in the brief settle it.

  1. "Novel application. Foundation models in a field that has not used them much, with an evaluation built for that field." — Requirements consistency checking is a largely pre-LLM literature. This is close to a textbook instance of the category.
  2. ★ "If your project uses an LLM as part of the method, describe that in the Method section instead." — The decisive line. The brief explicitly anticipates projects where the model is the method rather than a writing aid, and says where to describe it. A rule excluding such projects would not need that sentence to exist.
  3. "Workable: … inference up to about 8B in 4-bit … retrieval over corpora up to about 10 GB." — Inference-only work is listed as workable. No training requirement appears anywhere in the document.

Every figure in §3.2 is a property of a language model performing a task. The compiler is the independent variable; the model's accuracy, consistency and token consumption are the dependent ones. Three results follow, and none of them is a statement about software:

  • A single long prompt silently drops true conflicts as the corpus grows — a measured failure mode of long-context generative models, adjacent to the Lost in the Middle finding.
  • Verdicts shift with ordering and across repeats — LLM-as-judge reliability: positional bias, self-consistency, verdict stability.
  • ★ A small open model with structured decomposition versus a large model with one prompt — a capability-versus-scaffolding claim, which is squarely a foundation-models result.

The graph is the instrument. The study is about what the instrument measures.
