SDD Compiler · Lecture · Design input for code-ready graphs

How a coding agent reads specs, and what the spec graph must give it

A frontier coding agent (Claude Code, driving Haiku, Sonnet or Opus) is handed a set of SDD spec files and asked to build the system. This lecture follows what it actually does with them, where that process drops requirements or invents behaviour, and then asks the same questions of the spec graph. It ends with a small, bounded set of changes to the compiler's output, so the graph gives an agent everything the Markdown gives, plus the structure the Markdown lacks.

PART 0

The frame: two steps, one boundary

The compiler's job ends when the artifact is written. What an agent then does with that artifact is a separate step, run by a separate tool.

STEP 1: sdd-compiler                          STEP 2: any coding agent (separate)
Markdown specs ──sddc compile──► artifact ──┬─► Claude Code · Haiku / Sonnet / Opus ──► code + tests
                                 (frozen)   │
                                            └─ the same artifact for every model and every run

That boundary settles what "code-ready" means for the compiler. The compiler cannot make an agent write good code. It can only decide what the agent is given to read. So the whole lecture asks one question three times. First, what does an agent do with what it reads (Part 1)? Second, where does that go wrong (Part 2)? Third, what should the artifact contain so that less goes wrong (Parts 3–4)?

The one rule this lecture arrives at

The artifact must never give the agent less than the Markdown did. Beyond that, it should add only what the Markdown cannot give: a map, a checklist, one place per unit of work, and settled conflicts. Every proposal in Part 4 either restores something the rel01 graph loses or adds one of those four things.

PART 1

How a frontier agent consumes a folder of spec files

The benchmark case: ten Markdown spec files, an empty output directory and a prompt that says "build this". Nothing below is specific to the SDD Compiler.

1.1First, where an agent can keep anything

People say an agent "stores the specs internally". It does not, in any database sense. An agent built on a language model has exactly three places where information can live, and each behaves very differently:

PlaceWhat is in itHow long it lastsWhat that means for specs
The weightsEverything learned in training: languages, libraries, common designs, typical CLI conventionsFixed; your specs never enter itThis is the prior. When a spec is silent or vague, the gap is filled from here, and that is the root of most hallucination.
The context windowThe system prompt, tool definitions, CLAUDE.md, your prompt, and every file read, command output and message so far [4]One session; parts are cleared or summarized when it fills [4]This is the only working memory. A spec sentence influences the code only if it is in here, as text, when the code is written.
Files on diskThe specs themselves, plus anything the agent writes: plans, notes, task lists, the codePermanentExternal memory. It helps only if the agent reads it back. Anthropic calls this "structured note-taking" [3].

So "store internally" really means tokens sitting in the context window. While the model reads them, it computes internal representations (attention keys and values) over them. Those can be cached to save cost, but they are derived from the same text and add nothing to it. Each turn works from the text again. Everything else in this lecture follows from that.

1.2The eight stages of one build

Claude Code describes its loop as three blended phases: gather context, take action, verify results [4]. For a from-spec build it is useful to split them finer:

S1 Orient

Before any file is opened, the window already holds the system prompt, the tool definitions, CLAUDE.md and the task prompt [4]. Whatever these say about the specs ("the specs are in sdd/specs/, read the constitution first") is the agent's entire map at this point.

S2 Discover

The agent finds what to read with file tools: Glob for names (results capped at 100 files), Grep for content [5]. It sees file names and matching lines, not meaning. File names, folder layout and headings are therefore doing real work. Anthropic describes agents navigating by exactly these signals: "file sizes suggest complexity; naming conventions hint at purpose" [3].

S3 Read

Read returns file text with line numbers. If a file exceeds the tool's limit, the agent gets a first page and a PARTIAL view notice and must ask for more [5]. Every read appends text to the window. Nothing is filed away anywhere else. Ten spec files read in full means all ten files' text sits in the window, in the order read.

S4 Tokenize and attend

The text is split into subword tokens, the approach introduced for translation as byte-pair encoding [15]. Claude's own tokenizer is not published, so counts must come from the token-counting API, never from a ratio. Each generated token is then computed with attention over all tokens in the window [14]. There is no index. The model does not build a table of requirements. When it writes line 300 of store.py, the only way AC-4.7 influences that line is by being attended to, among everything else in the window, at that moment.

Attention is not uniform in practice. Models use information at the start and end of a long input better than information in the middle [6]. Performance degrades as input grows, often well before the advertised limit [7][8][9]. Irrelevant text in the window lowers accuracy even when the relevant text is present [10][9]. Anthropic calls the context an "attention budget" with "diminishing marginal returns" [3].

S5 Plan

Good practice, and the agent's own habit on large tasks, is to explore, then plan, then code [2]. The plan is a task list or a notes file. It is a compression: forty requirements become "implement the store module". From here on, the plan often steers more than the specs do, because it is shorter, more recent and phrased as instructions.

S6 Generate

Code is written one token at a time. Each token is predicted from the window plus the weights. Where the window states a precise answer (a function signature, a JSON field name, an exit code), the model can copy it. Where the window is silent or vague, the weights supply the most typical answer for that kind of program. That is usually plausible and often wrong for this spec.

S7 Verify

The agent runs tests, reads failures and edits. Claude Code's guidance is explicit that a runnable check is what lets the loop close without a human [2]. But in a from-scratch build the tests are usually written by the same agent from the same reading of the specs. They confirm the agent's interpretation, not the spec.

S8 Compact

When the window fills, Claude Code "clears older tool outputs first, then summarizes the conversation if needed. … detailed instructions from early in the conversation may be lost" [4]. Subagents are similar: they read in their own window and return only a summary [4][3]. Both are lossy by design, and the spec text, read early and never re-read, is the material most exposed.

1.3The same process at this repository's scale

This repository's own spec set is 10 Markdown files, 164,581 bytes, holding 191 acceptance criteria. How many tokens that is has not been measured. It is large enough that a full build reads a big share of the window with specs, then adds code and test output on top. Stages S3, S4 and S8 are therefore not edge cases at this size. They are the normal path.

PART 2

Where specs are missed, behaviour is invented, and code gets worse

The same eight stages, examined for the three failures the study will count. Ratings are judgements, with the reason and the evidence beside each.

2.1What the literature says the failures look like

Liu et al. built a taxonomy of hallucinations in LLM-generated code with three primary categories [11]. In their study the largest was requirement conflicting (39.6% of hallucinations): the code does something other than what was asked. Almost all of that was behaviour conflicting (35.4%). Next came knowledge hallucinations (34.9%), mostly wrong beliefs about libraries or the project (26.0%). Then code inconsistency (25.5%), such as undefined variables and useless statements. Those shares come from their setting, not ours. The shape still matters here: the biggest single class is the one a spec is supposed to prevent.

A narrower, sharper case is invented dependencies. Across 16 models, Spracklen et al. found hallucinated package names in at least 5.2% of samples for commercial models on average, and 21.7% for open-source ones [12].

Size matters too. On ClassEval, every model tested did much worse on whole classes than on single functions. Generating a whole class at once was the best strategy only for the strongest models, while weaker models did better method by method [13]. That is a direct hint for Haiku versus Opus. Smaller models are likely to benefit more from being handed one unit at a time, which is a prediction to test, not a result.

Three root causes under the table
  1. Nothing forces coverage. A folder of prose has no list of obligations the agent must account for. S2, S3, S5 and S8 all lose requirements silently. This is the missout cause.
  2. Gaps are filled from the prior. Missing formats, undefined words and unresolved contradictions reach S6 as silence, and the weights answer. This is the hallucination cause.
  3. Too much text, in the wrong order, at the wrong time. Everything is loaded early and competes for attention, then gets compacted. This drives both failures, and it gets worse as the spec set grows.

A spec artifact can act on all three causes. It cannot change the model or the agent's loop. It can change what exists to be read, how it is split, and what it tells the agent it still owes.

PART 3

When the specs are a graph: how an agent traverses it

The agent never sees a graph. It sees text returned by tools. "Traversal" is a sequence of reads, and the design question is what each read returns.

3.1What traversal physically is

An agent following an edge from node A to node B does this: it reads a record that mentions B, then decides to look B up, then issues a tool call (Grep "N-000807" or Read of the file that holds it), then gets text back that lands in the window. Each hop costs a round trip, adds tokens, and depends on the agent choosing to make it. SWE-agent's central result is that this interface matters: purpose-built commands for navigating and viewing changed how well the same model performed [16]. For the compiler, the artifact's file layout and ids are the agent's interface to the graph, and they deserve the same design care as the node schema.

3.2What the rel01 store looks like to an agent (measured)

Plainly

The rel01 store is a database for the compiler, not a reading format for an agent. Handed to Claude Code as-is, it loses on all three root causes of Part 2: less information (contracts, context), more text (about 21.6× the bytes), and more distraction (conflict noise, bookkeeping edges). If the study compared "Markdown" with "the rel01 store", the graph would be expected to lose, and that result would describe the export format, not the idea.

3.3Does the agent need a map? Yes

Three independent lines of evidence point the same way:

  • Aider's repository map gives the model a compact overview of the whole repository (files, key symbols and signatures), ranked by a graph algorithm and held to a token budget. Its purpose is to let the model "figure out which files it needs to look at" [17].
  • GraphRAG pre-computes summaries of clusters in an entity graph because plain retrieval fails on questions about the whole corpus [18]. "Build the whole system" is exactly such a question.
  • Anthropic's context-engineering guidance recommends keeping "lightweight identifiers" in context and loading detail "just in time", while noting that a hybrid, with some data up front, works best [3].

For a spec graph, a map fixes the two failures a folder cannot: it says what exists (stopping S2 and S3 losses) and in what order to build (giving S5 a spine). One caution from GraphRAG applies: its summaries are written by an LLM. A map written by a model is a new place to hallucinate. The spec map should be computed, not written: counts, ids, names and order, all deterministic.

3.4The traversal an agent should follow

Set this against Part 2. The map answers S2 and S3 (what exists). The checklist answers S5 and S8: the obligations are on disk, with ids, so a compaction cannot lose them, and a plan cannot quietly drop them. One pack per unit answers S4, because the agent reads only what the current unit needs, while it needs it, and the pack is small enough to sit near the end of the window, where it is used best [6][1]. Contracts carried verbatim, and conflicts settled before export, answer S6.

PART 4

What to add: six export changes, and nothing more

The store stays as it is. What changes is a new, deterministic agent export written next to it. Everything below is bounded to what the failure analysis requires.

4.1Six principles for the export

  1. Never less than the Markdown. Every byte of spec text reaches the export somewhere, verbatim. This is checkable: coverage of spec bytes is 100% or the export fails loudly.
  2. Structure, never new words. The export contains spec text, ids, counts and links, and nothing written by a model. The canonical forms and verdicts that are model output stay labelled as such. The compiler must not become a new source of hallucination.
  3. Small entry point, detail on demand. One map, then packs [3][17].
  4. One unit fits comfortably. A pack is sized in characters (the unit G3-3-traversal.md proposes) and should be no larger than the Markdown it replaces.
  5. Settled before served. No unadjudicated contradiction reaches the agent as a "question". Duplicates are shown once.
  6. Every obligation has an id to account for. The agent ends with a list, not a feeling.

PART 5

Guardrails: how the graph can win, and how not to fool ourselves

The goal is a graph that does not produce worse code. The way to reach it is by design and pilot, never by how results are reported.

5.1Where the graph should win, and where it should only tie

  • Clean, single-file specs: expect about a tie. With E1 the agent has the same information; the map and checklist may help coverage a little. Any loss here points to a format problem to fix, and is a reason to run the pilot below.
  • Messy, multi-file specs (duplicates, refinements scattered across files, contradictions): this is where the export does work the Markdown cannot. It gathers every claim about a unit from every file, shows duplicates once and delivers contradictions already settled. The study's clearest positive result, if there is one, lives here.
  • Smaller models: ClassEval's finding that incremental generation suits weaker models [13] predicts a larger gain for Haiku than for Opus. That is worth stating as a hypothesis in the proposal.

5.2Three checks before any study run

  1. Coverage check (E1): 100% of spec bytes appear in the export. If not, the run is invalid.
  2. Size check: total pack characters are no more than the Markdown's characters, and every pack is smaller than a set limit. This is measured, not assumed.
  3. Pilot A/B: one task, one model, Markdown versus export, before committing to the full grid. If the export loses, fix the export, then start the study. That is legitimate development, not tuning on the test set, provided the pilot task is excluded from the reported results.
Reporting

Whatever the full study finds is reported, including a tie or a loss on some condition. The course brief treats reporting only the runs that worked as misconduct. A controlled null result on clean specs, alongside a gain on messy ones, is also a stronger paper than an unexplained win.
