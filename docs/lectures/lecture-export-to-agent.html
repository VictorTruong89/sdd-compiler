From export to agent: how a many-file spec reaches Claude Code and gets read

The spec-graph export is not one file but twenty-odd. This lecture follows it from the disk to the model: which file the agent sees first, which file tells it how to read the rest, what the model does with every token it reads, and what four real agents actually opened. The aim is practical: make the export cheaper to read. Round 13c measured it at 5.0–5.3× the Markdown's words, and Haiku took 63–87 turns on it against 33–47 on the Markdown, without scoring higher.

The three answers
  1. How many files? The export task's spec/ holds 23 files for case006: MAP.md, CHECKLIST.md, export.meta.json and 20 packs. case010 has 26 files (23 packs) and case016 has 38 (35 packs). (Part 2.)
  2. Which file reaches the agent first? None of the spec files. The first thing the model sees from the task is instruction.md, which Harbor pipes into claude --print as the user message. Claude Code puts its own system prompt and tool definitions in front of it. The instruction then names spec/MAP.md as the place to start. (Part 3.)
  3. Which file says how to read the others? MAP.md. Its "How to use" section is the only reading instruction in the export, and the F7 spec makes it the entry point (§4.7, CT-7.4). It is written by map_md() in src/sdd_compiler/export/files.py. (Part 4.)
The finding that drives Part 6

All four case006 export runs read the specification text in full. Three of the four first stripped the export back to plain spec text with sed or awk. They kept only each pack's ## Text section and dropped the ↳ tag lines. No run read the 1,356-line "Claims to implement" list of the largest pack, and no run read CHECKLIST.md beyond its first 20–40 lines and a few greps. About 60% of the export's words (the claims lists and the checklist) went unread. The agents rebuilt something close to the Markdown by hand.

PART 1

How a model like Claude processes a prompt

The general part, for a reader new to the subject. Everything later rests on six facts: tokens, the context window, one token at a time, the agent loop, caching, and what long inputs do to accuracy.

1.1Tokens

A language model does not read characters or words. Text is first cut into tokens: pieces of words, whole short words, punctuation, spaces. Every size limit and every price is counted in tokens. Claude's tokenizer is not published, so a token count can only come from the API itself. It is reported in the usage field of every response, or by the token-counting endpoint [1]. This lecture therefore gives token figures only where a transcript recorded them, and uses words and characters for files.

1.2The context window

The context window is "all the text a language model can reference when generating a response, including the response itself" [1]. It is the model's only working memory. Everything in the request counts: "the system prompt, every message in messages (including tool results, images, and documents), and your tool definitions," and the output the model writes, thinking included [1]. Haiku 5.5 and Sonnet 5.5, the two models in round 13c, have a 1M-token window, and one request can write up to 128k output tokens [1].

Weights and context are different things. The weights hold what the model learned in training and never change during a run. The spec reaches the model only as text in the window. The earlier lecture develops this distinction (its §1.1).

1.3Reading everything, writing one token at a time

At every step the model computes over the whole window and produces one next token. That token is appended, and the model computes again. There is no index and no lookup table of requirements. A spec sentence influences a line of code only by being in the window when that line is written. The earlier lecture's stages S4 and S6 cover this in more detail.

1.4The agent loop

A coding agent wraps the model in a loop. Claude Code calls this "gather context, take action, verify results" and names the wrapper the agentic harness: "the layer around the model that provides the tools and manages the context the model sees" [2]. Mechanically, each pass is one API request:

1.5Why every file read is paid again on every turn, and what caching changes

The API keeps no memory between requests. Each request carries the whole conversation: "previous turns are preserved completely" and each response "becomes part of the input for the next turn" [1]. A 30,000-token spec file read at turn 3 is therefore part of the input at turn 4, turn 5, and every turn after it.

Prompt caching makes the repeat cheaper, not smaller. A request can resume "from specific prefixes" of an earlier one. The cache covers "tools, system, and messages (in that order)," and a hit requires "100% identical prompt segments" [3]. Reading from the cache costs "0.1 times the base input tokens price," with lower multipliers listed for some models (0.05× for Sonnet 5.5). Writing it costs 1.25× for a 5-minute entry or 2× for a 1-hour entry [3]. The round-13c transcripts show 1-hour cache writes (ephemeral_1h_input_tokens). Cached tokens still occupy the window: caching "changes what you pay for those tokens, not whether they count" [1].

The transcripts show this directly. Each request's input is split into input_tokens, cache_creation_input_tokens and cache_read_input_tokens. Summed over a run, the cache-read total is roughly the sum of every turn's prefix, and in round 13c it runs into the millions (Part 5). Every extra turn pays the whole accumulated prefix once more, at the cache-read rate.

1.6What happens as context fills

If input plus output reaches the window, generation stops [1]. Claude Code acts before that point: "It clears older tool outputs first, then summarizes the conversation if needed," and "detailed instructions from early in the conversation may be lost" [2]. In round 13c no case006 run came near this. The peak context was 336,197 tokens of a 1M window, and no transcript shows a compaction (Part 5). The pressure in these runs is cost, turns and attention, not overflow.

The model's own thinking also counts. On Haiku 5.5 and Sonnet 5.5 "the API keeps previous thinking blocks by default, and they count toward the context window" [1]. In the transcripts, one long planning thought per run (54k–128k output tokens) is the largest single block that any run adds (Part 5).

1.7What is known about long inputs

Each source below was opened on 2026-10-16 at its abstract or documentation page. Full texts were not read, so only what the abstract states is used.

  • Position. Performance "is often highest when relevant information occurs at the beginning or end of the input context." It drops when models must use information in the middle of long contexts [4].
  • Same content, longer input. Padding the same questions with extra text produced "a notable degradation in LLMs' reasoning performance at much shorter input lengths than their technical maximum" [5].
  • Advertised versus effective length. On RULER, "almost all models exhibit large performance drops as the context length increases" [6]. These are models from 2024; how Claude 5.5 models behave at these lengths is not measured here.
  • Irrelevant text. On math problems with distracting sentences, "model performance is dramatically decreased when irrelevant information is included" [7].
  • Anthropic's own wording. As token count grows, "accuracy and recall degrade, a phenomenon known as context rot" [1]. Context is "a finite resource" with an "attention budget," and the goal is "the smallest set of high-signal tokens that maximize the likelihood of your desired outcome" [8].

For the export, the inference is simple: words that the agent reads but does not need are not free, even when caching makes them cheap. How much they hurt the code on these tasks is to be measured. Round 13c gives no test-level evidence that they hurt (Part 5.6).

1.8Formatting sensitivity

The same content in a different template can change results. He et al. formatted identical contexts as plain text, Markdown, JSON and YAML and report that GPT-3.5-turbo's performance "varies by up to 40% in a code translation task depending on the prompt template," while larger models were "more robust" [9]. Sclar et al. found open-source models "extremely sensitive to subtle changes in prompt formatting in few-shot settings," with gaps up to 76 accuracy points [10]. Neither tested Claude or a coding agent. They show that format is a real variable, not which format is better for us.

1.9Maps for agents, and context engineering

  • Repository map (Aider). A compact list of files, key classes and functions and their signatures. It is ranked with a graph algorithm over file dependencies and held to a token budget (--map-tokens, 1k by default). The model uses it to understand the codebase and to ask for the files it needs [11].
  • GraphRAG. It builds an entity graph, then pre-generates summaries of related groups, because plain retrieval fails on questions about a whole corpus [12]. Its summaries are written by an LLM. Ours must not be (F7 §4.1 rule 2).
  • Agent-computer interface (SWE-agent). A custom interface for editing, navigating and running tests improved a fixed model's results. The authors argue that agents are a new kind of user who needs interfaces built for them [13]. For us, the export's file layout is that interface.
  • Context engineering. Anthropic's term for "curating and maintaining the optimal set of tokens" during inference. Its techniques: keep "lightweight identifiers (file paths, stored queries, web links, etc.)" and load detail just in time, use "progressive disclosure," compact, take structured notes, and clear tool results [8].

The earlier lecture already drew from these the case for a computed map, a checklist and one pack per unit. Part 5 tests that case against what agents actually did.

PART 3

Which file reaches the agent first

From instruction.md on the host to the first API request inside the container.

3.1The chain, step by step

  1. The task builder (notes/build_task.py) copies the export into the task's environment/spec/, which the Dockerfile copies to /app/spec. It writes instruction.md, whose only format-specific sentence is: "The specification is the compiled export in spec/. Start with spec/MAP.md; account for every id in spec/CHECKLIST.md." The Markdown task says instead: "The specification is the Markdown files in spec/: spec/Full_PRD.md, spec/Hardware_Requirements.md, spec/Interface_Contract.md." The rest is identical (build contract, PYTHONPATH=src, "Keep spec/ as it is", hidden tests).
  2. The driver (harness/trials/run_queue.sh, line 153) runs harbor run -p <task> -a claude-code -m <model> --ak version=2.1.296 --ak max_budget_usd=10 --ak disallowed_tools=…, with ANTHROPIC_API_KEY unset. trial.env pins Claude Code 2.1.296, a $10 ceiling and a 9,000 s run timeout.
  3. Harbor's Claude Code agent (harness/platforms/harbor/download/.venv/…/harbor/agents/installed/claude_code.py, run(), lines 1862–1976) takes the task's instruction text. It puts the text in an environment variable and runs, inside the container:
    printf "%s" "$instruction" | claude --verbose --output-format=stream-json <flags> --print 2>&1 | tee …/claude-code.txt
    The flags include --max-budget-usd, --disallowedTools and --permission-mode=bypassPermissions (the default, lines 91–102). Harbor also sets CLAUDE_CONFIG_DIR, so the session transcript lands in the saved job folder.
  4. Claude Code receives the instruction on standard input as the first user message. It sends the first API request, which holds its system prompt, the tool definitions, some attachments and the instruction.

The first user step in each transcript (agent/trajectory.json, step 1) is the text of instruction.md, word for word. No spec file is in the window when the model first runs. The first spec text arrives as the result of the model's own first tool call.

A side finding: the "partial build" run

haiku-case006-markdown-2 stopped after 26 turns ($0.11 est.), and TRIAL.md Finding 7 records it as a valid run that scored 0. The transcript shows why. Haiku's second request ended at the 128,000-token output limit inside one thought (stop_reason: max_tokens). Claude Code then injected "Output token limit hit. Resume directly…". PART 4

MAP.md is the reading instruction

Confirmed from three places: its text, the spec that governs it, and the code that writes it.

  • The spec. sdd/specs/ownership.yaml maps src/sdd_compiler/export/** to sdd/specs/F7_agent_export/spec.md. F7 §4.7 calls MAP.md "The entry point (CT-7.4)", and item 7, "How to use", is the fixed reading text.
  • The code. map_md() in src/sdd_compiler/export/files.py writes the sections in the CT-7.4 order and ends with "## How to use", HOW_TO_USE. No other export file contains reading instructions. Packs have only a header line, and CHECKLIST.md has one line: "Every id below must end implemented, tested, or listed as not done with a reason."
  • The text (case006):
## How to use

1. Read pack 00 (the foundation) first, if there is one, then each pack in the order of the table above.
2. Every id in `CHECKLIST.md` must end in one of three states: implemented, tested, or listed as
   not done with a reason.
3. Mark code with `# spec: <id>` beside what satisfies an id. …
4. Fields named *derived* (layer, modality, kind, relation) were assigned by the compiler. The
   verbatim text of a block wins over them.
5. A block tagged `no node` carries spec text that formed no claim; read it, it is still the spec.

4.1What the map does not tell the agent

  • Nothing to read first. case006 has no vision.md or constitution.md, so the map opens with "⚠ No foundation pack" and "Read first: None." Zero2Repo's files are named Full_PRD.md, Interface_Contract.md and Hardware_Requirements.md, and the default foundation_globs match none of them.
  • No sizes. The units table gives blocks and claims, not words. Every run measured the files itself (wc -c) before reading (Part 5.1).
  • Nothing about which part of a pack is the spec. "How to use" never says that ## Text is the full spec and the lists after it are indexes of the same text. The agents worked it out and cut the lists away.
  • One unit swamps the order. Pack 19 ("Feature points") holds 210 of 465 blocks, 677 of 1,012 nodes and 32,520 words. That is 43% of the export and 2.3× the whole Markdown. "Each pack in order" means one file the tools cannot return in one piece (Part 5.2).
  • A count that reads as a contradiction. The Contracts section lists 9 code blocks, while Counts says "contracts: 0". By F7 §4.8, counts.contracts counts CT- contract nodes, not code blocks. That is correct to the spec but easy to misread.

5.2Patterns

  • Everything is read before any code is written, in both formats. No run read pack by pack while building, which is the traversal the earlier lecture proposed (its Fig. 2). Each run read the whole spec in its first 1–10 requests, then wrote code.
  • The export is cut back to the Markdown. Three of four export runs extracted only ## Text, and two also removed the ↳ lines. The fourth, haiku-export-1, read whole packs for the small units, but for pack 19 it read only the Text lines.
  • Tool limits shaped the reading. Claude Code returns a Bash result inline "up to roughly 30,000 characters". Past that, the model gets a file path and a 2,000-character preview. Read returns at most 25,000 tokens per call and refuses a whole file over 256 KB [14]. Pack 19 (192,954 bytes) is under 256 KB but over the token limit, so it is read in pages. The Markdown runs hit the same Bash limit with cat and switched to Read. Every export run hit it on pack 19 and paged or saved to /tmp.
  • Re-reads are rare. No spec file was read in full twice. Only small re-reads occurred: line 300 of pack 19 twice in haiku-export-1, lines 2023–2035, and greps of CHECKLIST.
  • The checklist was counted, not read. At most its first 40 lines, plus grep and grep -c. haiku-export-1 wrote a SPEC_COVERAGE.md that accounts for the 1,012 ids by pack ranges, and it says so: "I did not mark every id individually." No run ticked items.
  • Never opened by any run: the "Claims to implement", "Related elsewhere" and "Terms" sections of pack 19, and CHECKLIST.md beyond line 40. Sonnet never opened export.meta.json.
  • The model knows the original. The spec never says "click". Six of the eight runs wrote the word into their code anyway (for example ClickException in sonnet-export-1). Recall of the public library affects both formats.

What the numbers say

  • The spec costs 31k tokens of context as Markdown. As the export it costs 42k–89k, depending on how much the agent cut away. Markdown runs went from 6.2k to 37.3k tokens. haiku-export-2, which kept only the Text without tag lines, went to 48.7k. The Sonnet export runs (Text only, with tag lines for packs 06+) went to 52.7k and 55.6k. haiku-export-1, which read whole packs, went to 95.6k.
  • One planning thought dominates every run's output. After reading, each run made one request whose output was 54k–128k tokens, nearly all hidden thinking. That happened in both formats (Haiku Markdown 110k and 128k; Haiku export 128k and 95k; Sonnet 54k–69k). Two Haiku runs hit the 128,000 cap (stop_reason: max_tokens). In haiku-export-1 the cut-off thought did not stay in context (the next request is +64 tokens). In haiku-export-2 the 94,689-token thought did stay (context 48,734 → 143,721), which fits the documentation that Haiku 5.5 keeps previous thinking [1].
  • Turns, not reading, drive the cache-read total. haiku-export-2 read the spec in 8 tool calls, as few as Sonnet did, yet made 63 requests. Its cache-read total (13.9M) is 1.8× haiku-markdown-1's (7.7M). The extra requests were writing, editing and smoke-testing code, not reading spec. Why Haiku wrote and tested in more, smaller steps on the export is not known. One candidate is the larger prefix after reading. Another is the instruction's "account for every id", which led haiku-export-1 into id-marking work (c52–c54). Neither is shown.
  • No compaction. The peak context was 336,197 tokens of 1M. Compaction, the risk the earlier lecture expected the checklist to guard against (its stage S8), did not occur.

5.5Round 13 had a different result, and why that matters

On case004 (round 13), the settled export was 6.1× the Markdown's words, yet Haiku's turns came down to 20–35, against 24–26 on the Markdown. Only the unsettled export there had 46–75 turns. So size alone does not explain the extra turns in round 13c. case004's export is 30,875 words, and case006's is 75,090 with one 32,520-word pack. Whether the difference comes from absolute size, from the oversized pack, or from something else is to be measured.

5.6And the tests

The format changed no test in case010 or case016. In case006 it changed 5 for Haiku: 2 gains (a required prompting option; UUID inference) and 3 losses (completion items printed as objects; one help-text ellipsis). In each of these the rule is present in both formats (TRIAL.md, "Why tests fail"). Nothing in the reading traces explains the 3 losses. Both export runs read the relevant Text, pack 12 and pack 19 in full.

Combined, and the recommendation

Add X4 so that no unit outruns the tools, and X5 so the agent does not have to guess.

Recommendation: X1–X5 together, then rerun the four Haiku case006 runs. What it drops: the export stops restating node texts. Anyone who wants a node's words in isolation must look them up in the Text or in the store. It can show a turn and token effect of the size seen here (63–87 against 33–47).

What none of this addresses

Round 13c's failing tests are mostly rules that the model misses in both formats (TRIAL Finding 4), not reading failures. A smaller export should cut cost and turns. It is not expected to raise scores on clean, single-author specifications. The case for the graph still rests on messy specifications, where the export gathers and settles what the Markdown scatters.

GLOSSARY

Words used here

TokenThe unit a model reads and writes: a word piece, short word or symbol. Limits and prices are in tokens
Context windowEverything the model can see in one request, its own output included. 1M tokens for Haiku 5.5 and Sonnet 5.5 [1]
Request / turnA request is one API call. A "turn" in this repo's tables is Claude Code's num_turns, which is close to but not equal to the number of requests
Tool call / tool resultThe model asks Claude Code to run Read, Bash, Write or Edit. The output comes back as text appended to the context
Prompt cachingReuse of an identical prefix from an earlier request, billed at a fraction of the input price. Cached tokens still fill the window [3]
CompactionClaude Code clearing old tool output and then summarising when the window fills [2]
ThinkingOutput the model writes before acting, not shown in our transcripts. Counted as output, and kept in context on the 5.5 models [1]
HarborThe platform that builds a task's container, runs the agent with instruction.md, and scores it with hidden tests
Exportsddc export output: MAP.md, CHECKLIST.md, export.meta.json, packs/ (F7)
Pack / unitA unit is a source file × second-level heading. A pack is the Markdown file for one unit
Node / claim / ↳ tag lineA node is one atomic claim the compiler extracted from a block of spec text. The tag line under a block lists that block's node ids
Persisted outputA Bash result too large to return inline. Claude Code saves it to a file and returns a path and a 2,000-character preview [14]
