Tiered Markdown or a spec graph?

A fair comparison against the method already running in collective-investment-ai-assistant: separate spec files per tier and feature. Five criteria, measured where possible. Then: how to store a graph so AI agents can use it, and how a human can see a thousand specs in thirty families without drowning. PART 0

A premise worth checking before comparing

The question starts from "a spec graph is certainly better than a flat long prompt". That premise is plausible, but it is less certain than it sounds, and it matters for how the real comparison is framed.

Three reasons the premise is weaker than it sounds:

  • It was never measured. The coverage and token figures from the earlier discussion (72% vs 93% and so on) were illustrative inventions. The direction is plausible, but the size of the effect is unknown.
  • "Flat long prompt" is not what agents do any more. A coding agent like Claude Code does not receive one pasted document. It greps, opens files, follows references and plans. The honest baseline is an agent working over well-organized Markdown files, which is exactly the method this lecture compares against.
  • The graph can lose things a file keeps. A file carries its reasoning, its rejected options and its tone of warning ("⚠ the adapter does not catch, soften or de-rate it"). Atoms and canonical forms can strip that out. Part 2 shows this is not a small point.
So the real question is

Not "graph or flat prompt", but: does compiling a graph over well-tiered Markdown add enough to justify its cost, and what does it risk losing?

The acceptance criteria, the part that atomizes most naturally, are about a sixth of a spec. Decisions and their rejected alternatives are nearly a third. A graph that carries atoms well but treats decisions as "annotations" would drop the largest part of what these specs contain, and the part that stops an agent from re-proposing something already rejected. The working design lists "where are decisions recorded?" as an open question. This measurement promotes it to a required node kind.

These defects were found, which says the method plus hand-written checks works. They were found late, and each needed a new tool, which says the relations were never checked by construction. Every one of the four classes is something a compiled graph checks as a matter of course: unique ids, a declared registry, links that must resolve, and one definition per claim.

PART 2

Five criteria, compared honestly

For each criterion: how tiered Markdown does it, how a compiled graph does it, where each fails, and a verdict in words. "Graph" below means the design in core-working-principle.md, not an idealized one.

2.1Token consumption

(a) Producing the structure

Tiered Markdown: no cost beyond writing the specs. The structure is the writing. The hidden cost is the hand-written check tools and the review sessions that found the defects in §1.4.

Graph: the specs are still written, plus a compile cost paid in agent questions:

compile tokens ≈ Σ blocks  × tokens(Q-ATOM)
               + Σ atoms   × tokens(Q-DESC)
               + Σ new terms × tokens(Q-TERM)
               + Σ candidate pairs × tokens(Q-PAIR)

# one-time for the existing corpus; afterwards only CHANGED blocks
# and their candidate pairs — the judgment lock makes rebuilds free

For scale, the twelve spec files total about 305 KB, roughly 76 thousand tokens by the rough rule. Each Q-DESC sends one atom and its block, not a file. The term that can explode is candidate pairs. It grows with how candidates are generated, which is exactly why candidate generation is the design's main measured risk.

(b) Consuming the specs while coding

Tiered Markdown: the hook sets a floor per session. Before editing code governed by F9, the agent must read the constitution plus F9, and CLAUDE.md is already loaded:

Session readingBytes≈ tokens (÷4)
Smallest spec (F9) + constitution + CLAUDE.md47,720~12k
Largest spec (F2) + constitution + CLAUDE.md70,093~18k
…plus vision.md ("read before proposing")+21,816+~5k
…plus each cited spec the agent chases+15–37k per spec+~4–9k each

The floor is paid again in every new session, by design. But these files are stable, and stable text is what prompt caching rewards: repeated reads of an unchanged constitution are much cheaper than the raw count suggests.

Graph: a context pack contains only what a recipe reaches. It will usually be smaller than a whole spec plus the constitution, because it carries the relevant constraints rather than all of them. Two costs push back. Packs differ per task, so they cache less well. And if decisions are included (they should be, §1.2), the pack grows toward the file it replaced.

Verdict · tokens

Producing: Markdown is cheaper. The graph adds a compile cost that is one-time plus incremental. Consuming: the graph is likely smaller per task, but the margin is unknown and shrinks once rationale is included and caching is considered. Not a decisive criterion either way until measured.

2.2Ease for the agent to assemble the right context

Tiered Markdown: routing is excellent at the coarse level. ownership.yaml maps a code path to one spec (first match wins), and the hook enforces the read. Below that level it is manual:

  • Outbound references must be chased by hand: every RA-67, QR-16, F1 CT-1.4. Some point into another repository.
  • Inbound references, "who depends on me?", have no index at all. The only tool is a grep across every file, which works for ids and fails for relations nobody wrote as an id.
  • Constraints are "all of the constitution", not "the ones that apply to this code", so the agent must judge applicability itself.

Graph: a recipe computes the set: core, contracts, constraints in scope, data, verification, boundary. It does this in both directions, and it says what it cut. The weakness is that a recipe can only follow links that exist. A relation the atomizer or the pair judge missed is missing from the pack, where a whole-file read would at least have put the sentence in front of the agent.

Verdict · context assembly

Graph, clearly, for inbound relations and scoped constraints, which Markdown cannot index. Markdown holds its own for "everything about this one feature", because the feature file already is that set.

Verdict · miss-out and hallucination

They fail in different places. Markdown misses across files and trusts unverified links. The graph misses where its own links are missing and adds an extraction step that can hallucinate. The graph's failures are checkable (resolution, manifest, guards). Markdown's cross-file misses are not, without hand-written tools.

2.4Risk of misunderstanding specs and their relationships

Tiered Markdown expresses relationships in prose: "wraps this", "gates F6b", "one prompt, two transports", "(RA-67, AC-1.77)". A citation says that two things are related, never how. Is RA-67 a constraint on AC-F9.4, the rule it refines, or a rejected alternative? The reader infers it. Identity itself can break: the AC-F9.6 collision meant one id named two claims, and an implementation satisfied the wrong one.

A graph makes relations typed (refines, constrains, conflicts_with) and identities unique by construction. Its own risk is false precision: a typed edge produced by an agent judgment looks authoritative even when wrong. A canonical form can also flatten nuance. "MUST propagate the error" loses "⚠ does not catch, soften or de-rate it", and those three verbs are the actual risk.

Verdict · relationships

Graph for identity and relation type. Markdown for nuance of meaning. The graph must therefore keep the verbatim source one hop from every node (level 3), and every typed edge must carry its rationale and the quote it rests on.

2.7What would settle it

A small, honest experiment on the real repository, run before any claim of superiority is written into the vision:

  • Tasks: a set of real coding and change tasks, each with a known answer set: which ACs, contracts, constraints and decisions the correct change must respect.
  • Arms: (A) agent with the files, the hook and grep, which is today's method; (B) the same agent with the same files plus graph queries and context packs.
  • Measure: tokens read; share of the answer set present in context; constraints violated in the resulting change; rejected options re-proposed; wrong relationship claims; lookups needed to find a given spec.

Arm B adds to arm A rather than replacing it. That framing is deliberate, and Part 3 explains why.

PART 3

The synthesis: compile the graph over tiered Markdown

The comparison is not a contest. The strengths do not overlap, so the right design keeps both.

P-0 already says prose is the source of truth and the graph is compiled. The comparison sharpens what that means:

Keep from tiered MarkdownAdd from the graph
Files as the authoring and reading unit: one feature, one file, fixed sectionsAtoms as the checking and linking unit
Stable human ids (AC-F9.3). The compiler adopts them as node ids when present (U1)Guaranteed uniqueness and a declared id registry: collisions fail the build
Decisions with rejected options, travelling with the featureDecisions as nodes linked to the claims they changed, so recipes carry them
Whole-file reads when the task is "this feature"Scoped packs when the task crosses features; inbound links; constraints in scope
Hooks that force reading the governing specHooks that can also hand over the context pack and manifest
Nothing requires toolingGenerated Markdown views, so even a tool-less agent benefits
Consequence for U1 (generic)

A project like collective-investment-ai-assistant should be compilable as it is. Its section numbers become layer hints in the project profile, its existing ids become node ids, ownership.yaml becomes component allocation, and its hand-written checks become compiler passes it no longer has to maintain. If adopting the compiler required rewriting the specs, U1 would have failed.

PART 4

Storing the graph for AI-friendly use

Where the graph lives on disk decides whether agents can use it with plain file tools, whether git diffs are readable, and whether queries are fast.

4.1What "AI-friendly" requires

  1. One record is one complete, self-describing unit an agent can read without loading its neighbours.
  2. Small addressable pieces, so reading one family never means reading all thirty.
  3. Plain text, deterministic order, fixed key order, so a git diff shows exactly the nodes that changed and an unchanged graph is byte-identical.
  4. Greppable ids, so the tool-less path still works.
  5. Queryable, so a tooled agent asks questions instead of opening files.
  6. Generated, never hand-edited, per P-0.

4.2The options

FormatStrengthWeaknessRole
One big JSON fileSimple to loadUnreadable diffs; an agent must load everythingrejected
JSON Lines, sharded by familyOne line = one record; diffs per node; greppable; one family per fileNot queryable by itselfrecord of truth
One YAML/MD file per nodeVery readableA thousand files; noisy tree; slow to scannot as record
SQLiteFast queries, indexes, joinsBinary in git: no diffs, no mergesderived cache, git-ignored
Graph database (e.g. Neo4j)Rich traversalA server to run; not files; overkill at this sizerejected for release 1
Generated Markdown viewsReadable by humans and tool-less agentsRead-onlyviews

4.3Proposed layout

.sdd/                              # next to the specs, committed to git
  graph.meta.json                  # compiler + schema + question versions, source hashes, counts
  profile.yaml                     # project profile (U1) — the only hand-edited file here
  terms.jsonl                      # term registry, one term per line, sorted by id
  nodes/<family>.jsonl             # one node per line, sorted by id
  edges/<family>.jsonl             # edges stored with the family of their SOURCE node
  lock/<kind>.jsonl                # judgment lock, one answer per line
  views/                           # GENERATED Markdown — do not edit
    map.md                         # level 0
    families/<family>.md           # level 1 cards, with node ids and source links
  cache/index.sqlite               # derived, git-ignored, rebuilt on demand

One node, one line (wrapped here for reading):

# illustrative — spans, family and terms are not compiled values
{"id":"AC-F9.3","kind":"requirement","layer":"L1","family":"thesis_source",
 "components":["term:RelayAdapter"],"terms":["term:thesis","term:RelayContradictedError"],
 "source":{"file":"sdd/specs/F9_thesis_source_port/spec.md","spans":[[6120,6498]]},
 "canonical":{"subject":"term:RelayAdapter","modality":"MUST NOT","response":"catch, soften or de-rate RelayContradictedError","trigger":"a relayed claim contradicts pipeline data"},
 "check_status":"clean","judgments":["q-desc:9f2c…"]}

4.4Why these choices

  • Shard by family, not by layer or source file. Most tasks are per subject, so an agent without tools opens one family file. It also keeps git diffs local to the feature that changed. A family re-derivation that moves a node shows up as a move, which is itself a useful review signal.
  • Edges live with their source node's family, so every edge has exactly one home and no file duplicates another.
  • Ids never embed the family or layer. Those can change; an id cannot. Where the project already has ids (AC-F9.3), the compiler adopts them; elsewhere it assigns opaque sequential ids.
  • SQLite is a cache, never the truth. Delete it and nothing is lost; the next query rebuilds it.
  • Views are how tool-less agents benefit. An agent that reads views/families/thesis_source.md gets the level-1 card with ids it can grep, without any MCP server running.
  • How agents use it, in order of preference: (1) queries through the agent integration (O3); (2) generated views; (3) grep on JSONL by id. All three return the same facts.
Size, honestly

A node line with canonical fields and spans is likely a few hundred bytes to a couple of kilobytes. A thousand nodes is then on the order of a megabyte of JSONL: small for git, small for SQLite, and far too large for an agent to read whole, which is the point of shards and queries. The per-line size is an estimate from the schema, not a measurement.

PART 5

Seeing a thousand specs in thirty families

Drawing 1,000 nodes and several thousand edges at once produces a hairball: technically complete, humanly useless. The answer is aggregation first, then drill-down.

5.1The principle: overview first, zoom and filter, details on demand

This sentence is a well-known rule from information visualization research, usually credited to Ben Shneiderman (to verify). It maps directly onto the disclosure levels already in the design. The visualization is simply those levels drawn.

ViewShowsItems on screenAnswers

V2 · Family map30 family bubbles; size = members; edges = aggregated cross-family links, thickness = count30 nodes"Which subjects are entangled?"
V3 · Family lanesOne family's ~30 nodes in horizontal layer lanes; refines edges vertical; other families as collapsed stubs at the edge~30 nodes + stubs"How is this feature built up, top to bottom?"
V4 · Node focusOne node, its 1–2 hop neighbourhood, all edge types, source text panel< 20 nodes"What touches this, and what does it actually say?"
V5 · Component matrixComponents × families; cell = allocated nodessmall matrix"What does this service owe to which features?"

V7 · U5 diffV1 with cells coloured by comparison outcome240 cells"Where does as-built diverge from design?"

5.2Rules that keep a large graph legible

  • Never draw all 1,000 at once by default. V1 and V2 are the entry points. Every larger drawing is a filter result.
  • Families are compound nodes that expand and collapse. A collapsed family is one bubble with a member count.
  • Layout is stable across compiles. Positions are computed deterministically and cached, so adding one spec does not reshuffle the picture the reader has memorized. Preserving the reader's mental map matters more than an optimal layout.
  • Lanes, not force layouts, for one family. Layer is meaningful, so it is a fixed axis. Force-directed layouts put nodes wherever physics lands them and hide the refinement structure.
  • Edges are filterable by type, with cross-family edges aggregated into one counted edge until expanded.
  • Colour means status only, one meaning everywhere: clean, ambiguous, stale, conflicted, empty. Layer and family are position, never colour.
  • Every visual item links to text: the node view and the verbatim source. The picture is for navigation. Reading happens in text.

PART 6

The study: one agent, three ways of holding the specs

The comparison in Parts 1–3 becomes a controlled experiment. This part fixes what is compared and what must be held constant. Parts 7–10 cover what to measure, how to measure it with Claude Code, what can go wrong, and how to count mistakes.

Course-project context. This comparison is the core of the MIA 5150 project. It stays out of vision.md, by the owner's decision. Citation status: every source in Parts 6–10 was opened and checked on 2026-09-13, and §10.9 lists them with links. One automated summary returned an invented taxonomy for a paper; reading the PDF itself exposed it. That is exactly the failure this study measures, and it is why every citation below was checked against the paper itself.

6.1The three arms

ArmWhat the agent getsHow it reaches a spec
F · Flat long MarkdownOne file holding every spec, in a fixed orderReads the file (whole, or in chunks)
T · Tiered MarkdownVision, constitution and one file per feature, laid out as in collective-investment-ai-assistantOpens files, greps, follows cited ids
G · Spec graphThe compiled graph (Part 4 layout) plus query toolsQueries: map, family card, node, context pack

6.2Three confounds that would invalidate the comparison

  1. Content. If one arm's specs say something the others' do not, the study measures authoring, not representation. Control: generate all three arms from one canonical source, and run an automated equivalence check that every gold atom and every relation is present in every arm (§10.1).
  2. Access mechanism versus representation. Arm G differs from T in two ways at once: the structure and a query tool. A win for G could come from the tool alone. Control: add an ablation arm G-v, the graph's generated Markdown views (map, family cards) as plain files, with no query tool. Now T → G-v isolates structure, and G-v → G isolates tooling.
  3. Format. The surface format of a prompt alone can swing performance widely. Sclar et al. (ICLR 2024) report differences of up to 76 accuracy points from formatting changes on LLaMA-2-13B. He et al. (2024) report up to 40% variation on a code-translation task across plain text, Markdown, JSON and YAML templates, with larger models more robust. Control: keep node text in the same Markdown prose in all arms. Only structure and access change, never the serialization of a claim.

6.3Holding the agent constant

Held constantHow, in Claude Code
Model and effortPin the model id and effort level on every run; record both from the telemetry model and effort fields (§8.2)
Ambient context--bare skips auto-discovery of CLAUDE.md, hooks, skills, plugins, MCP servers and auto memory, so a developer's own setup cannot leak in. The study's hooks and MCP servers are then passed explicitly with --settings and --mcp-config

StochasticityNot controllable. Ouyang et al. (TOSEM 2024) found that setting temperature to 0 still does not guarantee determinism in code generation. Response: repeat every (task, arm) several times and analyse at the run level (§10.6)
The one-sentence test, filled in as a draft

We claim that structuring specifications as a compiled graph, rather than as tiered or flat Markdown, reduces specification-grounded errors in code produced by the same coding agent, and we will show it by measuring acceptance-criterion pass rate, trap-violation rate and hallucination counts, with token cost as a secondary outcome, against flat and tiered Markdown arms with identical content, on a purpose-built specification corpus with hidden acceptance tests and planted traps. The claim stays hypothetical until measured; a null result is a valid finding.

PART 7

Metrics from the literature — reading, then generating

The agent's work has two stages that fail differently. First it finds and understands the relevant specs. Then it writes code that honours them. Each stage has an established family of metrics, and each needs adapting to specs.

7.1Stage 1 — reading the specs

Three research lines supply the metrics. Retrieval evaluation asks whether the right context was found. Long-context studies ask whether found context is actually used. Factuality evaluation asks whether what the agent says the specs require is true.

A trap in the reading metrics

In arm F the whole file is loaded, so loaded-context recall is trivially 100% and says nothing. What differs between arms is whether loaded content is used. So reading is scored at two levels. Retrieved means what the agent opened, taken from logs (§8). Identified means what the agent explicitly names as governing the task, taken from a structured answer. Identified recall and precision are the comparable reading metrics across all arms.

7.4Reliability of the measurement itself

  • Uncertainty on every number. Miller (Anthropic, 2024) argues that evaluations are experiments. He recommends confidence intervals, paired comparisons when arms share questions, clustered standard errors when questions come in groups, and power analysis before running.
  • Agreement between human annotators. Error labels need two annotators and an agreement statistic. MAST (Cemri et al., NeurIPS 2025) built its failure taxonomy from expert-annotated traces and reports Cohen's κ = 0.88.
  • LLM-as-judge, if used. Zheng et al. (NeurIPS 2023) document position, verbosity and self-enhancement biases, alongside over 80% agreement with human preferences for strong judges. Use LLM judging only for triage, calibrated against human labels on a sample.

8.3What cannot be measured, and what to do about it

  • Reading is not attending. Logs show what entered the context, never what the model actually used. Response: the identified-level metrics and the traps are behavioural evidence of use.
  • Cost figures are estimates. The documentation states total_cost_usd is computed client-side from a bundled price table and can drift from the bill. Response: report tokens as primary and cost as derived. Reconcile totals once against the Usage and Cost API.
  • The transcript can lag. The documentation notes it is written asynchronously. Response: read final text from Stop's last_assistant_message or the headless result, not from the transcript mid-run.
  • No sampling control. Treat every run as a stochastic draw (§6.3, §10.6).
  • Model and tool versions change over time. Record the Claude Code version and the model id per request. Run all arms interleaved over the same days, never arm by arm.
  • Privacy. Enabling prompt, response and tool-content logging exports spec text and code to wherever telemetry goes. Response: keep the collector local.

8.4A minimal run harness

# one run = one (task, arm, repetition), in a fresh worktree

cd runs/$RUN_ID && prepare_arm $ARM
#   $ARM is F | T | G-v | G and lays out the specs for that arm

# study/hooks.json      : PostToolUse, PreCompact, InstructionsLoaded loggers

PART 10

Experiment design: counting the mistakes

A study that counts mistakes needs four things built before any run: a corpus with known answers, traps that provoke specific failures, a scoring pipeline, and a statistical plan chosen in advance.

10.1The corpus — one source, four renderings

  1. A purpose-built product specification of moderate size: several features, each with contracts, acceptance criteria, decisions with rejected options, and cross-cutting constraints. It follows the section shape of collective-investment-ai-assistant so tiered Markdown is realistic.
  2. A reference implementation and hidden tests for each AC, written before any agent run.
  3. One canonical source (the tiered files) from which the other arms are generated. F concatenates the files in a fixed order, with trap positions controlled. G-v and G compile the graph and its views.
  4. An equivalence check: every gold atom, id and relation is found in every arm. The study does not start until this passes.
  5. Optional external validity: reading-only tasks on the real collective-investment-ai-assistant specs, which need no implementation. Decide what may be published first, since that repository has commercial intent and the course requires a public code link.

Traps must not look like traps

If traps are stylistically different from ordinary specs, a capable model may spot them and pay special attention, which inflates every arm. Write them in the same voice as their neighbours, and have someone who did not write them try to find them before the study.

10.4Making the hidden tests trustworthy

  • One or more tests per AC, including boundaries and negative cases, each tagged with the AC and the trap it covers.
  • Mutation check: deliberately break the reference implementation in ways that violate each AC. Every mutant must be caught by at least one test, or that AC's tests are too weak. This is EvalPlus's lesson applied at small scale.
  • Solvability review (M3): someone who did not write the task confirms it is solvable from the specs alone.

StepAutomatedHuman
1 CorrectnessHidden tests → AC pass, resolved, regressions—

Units of counting. The unit of observation is one run = (task, arm, repetition). For each run, record binary outcomes (resolved, each trap violated or not), counts (hallucinations by category, ACs failed), and continuous values (tokens, cost, turns). Report error rates per task, per AC and per trap, never raw totals across arms with different task counts.

10.6Statistical plan, fixed before the runs

  • Paired design. Every task runs in every arm, so arms are compared within task. This removes task difficulty as a source of noise, as Miller (2024) recommends for questions shared across compared systems.
  • Repetitions. Several runs per (task, arm) give pass^k and a per-task success probability. Choose the number with a power estimate from pilot variance, not a round number.
  • Clustering. Runs within a task are correlated. Use task-clustered bootstrap confidence intervals, or a mixed-effects logistic model with task as a random effect, for binary outcomes.
  • Paired binary comparisons. For "trap violated: arm T versus arm G" on the same task, use McNemar's test or the clustered bootstrap.
  • Multiple comparisons. Four arms and several metrics invite false positives. Name one primary metric in advance; treat the rest as secondary and correct for multiplicity.
  • Report everything. The course rules count reporting only the runs that worked as misconduct. Keep every run, and state exclusions and their reasons before looking at outcomes.

10.7Budget, stated as arithmetic, not guesses

runs          = tasks × arms × repetitions
tokens        = Σ_runs (input + output + cache_read + cache_write)   # measured in the pilot
estimated USD = Σ_runs cost_usd                                      # reconciled once with the Usage and Cost API
annotation    = runs × minutes per run to label × 2 annotators

A Claude Code run is billed in API usage, not GPU hours. The course's hardware section is about local GPU jobs, so the proposal should show this token arithmetic from the pilot rather than a GPU estimate. If a local open-weights model is added as a second agent later, its runs need their own GPU-hour arithmetic.

10.8The two-day trial, as the brief requires

  1. One small feature (a handful of ACs, two traps), arms T and G-v only, three runs each.
  2. Build the harness in §8.4 far enough to capture hook logs, stream JSON and hidden test results.
  3. Print one number: for example, trap-violation rate per arm, or identified recall of governing specs. Record the tokens per run. Those figures size the real study.
