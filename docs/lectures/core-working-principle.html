PART 0

The frame: what is being compiled, and who does which half

Before the three questions, two decisions shape every answer: what the source of truth is, and where the line between judgment and computation falls.

0.1The compiler analogy, made exact

The word "compiler" has been used loosely. It is worth making precise, because the precise version dictates the architecture.

Program compilerSDD CompilerWho does it
Source filesSpec documents in prose (markdown), written by one human or one AI at a timeAuthor
Lexing / parsingAtomization — prose → atomic nodes (Part 1)Agent judges, compiler guards
Symbol tableTerm registry — canonical names of actors, entities, components (§2.5)Agent proposes, compiler resolves
Semantic analysisPlacement and linking — layer, family, typed edges, conflicts (Part 2)Agent judges small questions, compiler maps
Intermediate representationThe spec graphCompiler
Back endsContext packs for code generation (U7) · diff against the as-built graph (U5)Compiler
P-0 · Prose is the source, the graph is compiled

The markdown spec files stay the source of truth. The graph is a build artifact derived from them, stored as plain text so it versions in git alongside the specs. Nobody edits the graph by hand.

Why: U1 — every spec-driven project already has prose files, so adoption needs no new editor. Single writer — no concurrent graph editing to reconcile. U5 — an as-built spec set is also prose, so both sides enter by the same door. Cost: a change must always round-trip through prose; there is no "just fix the edge" shortcut. That cost is the discipline.

0.2The boundary: judgment belongs to the agent, structure to the compiler

For release 1, vision.md O1 says the compiler's code is deterministic, and O2 says every language judgment is made by the user's own AI agent. Taken together they force a specific shape: the compiler never asks an open question. It asks the agent small, closed, schema-bound questions, checks each answer the moment it arrives, and does everything else itself. If a check fails, the compiler re-asks once, quoting the failed check. If it fails again, the item goes to the author with the failure shown. It is never accepted silently.

O1 relaxes in later releases

Later releases may deploy local ML models, such as embedding or small classification models, to help build the graph. Nothing in this design stops that, provided two conditions hold. Such a model is pinned to a version and its outputs go into the same judgment lock. And it suggests: extra candidate pairs, alias proposals, a second opinion on layer answers. The design keeps family, layer and link decisions on answers that can be audited.

The judgment lock — how O1 survives a non-deterministic agent

An agent asked the same question twice may answer differently. If the graph were rebuilt by re-asking, it would drift on every build, and U5's comparison would measure that drift instead of real divergence. The fix is borrowed from package managers' lockfiles.

# one record per agent judgment, stored beside the graph
judgment:
  kind:        atomize | describe | judge_pair | ...
  input_hash:  sha256(exact input text + question schema version)
  agent:       claude-code
  model:       <as reported by the agent>
  prompt_ver:  atomize/3
  answer:      { ... schema-validated ... }
  confirmed:   author | auto
P-1 · Judgment lock

Rebuilding the graph replays locked judgments; the agent is asked again only when an input hash changes or a question schema version is bumped. Given the same sources and the same lock, the build is byte-identical. Determinism is achieved by recording the non-deterministic part, not by pretending it is absent.

PART 1

Atomize: splitting prose into atomic specs

The hardest step, and the one whose errors propagate everywhere. The principle: the agent proposes the split, but the compiler can mechanically catch most of the ways a split goes wrong.

1.1What an atom is — four tests

An atomic spec is one claim that can be judged true or false on its own. "One sentence" is not the definition — a sentence can hold three claims, and one claim can need two sentences. Requirements-engineering standards describe a good requirement as singular, unambiguous and verifiable (ISO/IEC/IEEE 29148 — to verify). Those adjectives become operational tests:

TestQuestionIf it fails
T1 · Single verdictCould one observation or one test decide pass/fail for the whole statement?Split along the separate verdicts
T2 · Independent changeCould a stakeholder plausibly change or dispute one part while keeping the other?Split — otherwise a later edit silently changes a claim nobody meant to touch
T3 · Single layerDoes the whole statement answer exactly one layer question (§2.3)?Split — a statement that is both a contract and an architecture decision is two claims
T4 · Stands aloneAfter resolving pronouns and ellipsis, does each piece still mean something by itself?Do not split — the fragment is not a claim

T1–T3 push toward splitting; T4 is the brake. T3 is the interesting one: it makes atomization and placement check each other. If the layer questionnaire (§2.3) gets two "yes" answers at different layers, the atom was not atomic.

Worked cases

InputAtomsDeciding test
"Users can upload files and share them through a link."2 — upload; share via linkT1: two verdicts
"Downloads are served through signed URLs that expire after one hour."2 — delivery via signed URL; signed-URL lifetime is 1 hT2: the 1 h can be disputed while signing is kept
"Admins and file owners can delete a file."1 — subject is the set {admin, owner}T4 + list rule (below)
"The total size of all files in a workspace must not exceed 5 GB."1Collective reading: the claim is about the total, not each file
"POST /files stores the binary in S3."2 — contract of POST /files; binary storage is S3T3: L3 and L2
"Shared links expire automatically for security compliance."1 atom + 1 rationale annotation"for security compliance" is a reason, not a claim (§1.2)
Fresh · differs from discussion 1

Discussion 1 kept "signed URLs that expire after 1 hour" as one node, calling it "a single mechanism". Under T2 it splits, and its own worked example showed why that matters: it later could not tell whether the 1-hour part conflicted with a 30-day link validity. A claim that can be disputed on its own deserves its own identity.

List rule

Split on distinct obligations, not on distinct list members. Members that share the same obligation under the same condition stay one node with a set-valued field. The moment one member gets a different condition ("admins always; owners only within 30 days"), it is two obligations and T2 splits it.

1.2Not every sentence is a requirement — sentence roles

A spec document mixes claims with reasons, examples and context. Treating every sentence as a node floods the graph with things that can never be verified or conflict. The agent first labels each sentence with a role; the role decides what the compiler does with it.

RoleExampleBecomes
requirement"The share link returns 404 once expired."Node
constraint"No endpoint may respond slower than 300 ms."Node in C (cross-cutting, §2.2)
assumption"Every user has a verified email address."Node, kind assumption — ★ assumptions can be contradicted later, which is exactly the class discussion 1 called "undetectable"
definition"A workspace is a set of files owned by one team."Term registry entry (§2.5), not a node
rationale"…because users rarely check email at once."Annotation on the node it justifies
example"e.g. a 2 GB video"Annotation — useful later as a test seed
context / heading"We are building a file sharing service."Document context, not a node
open question"TBD: do guests need accounts?"Flag on the section; nearby nodes marked ambiguous
Fresh · assumptions are first-class

Neither earlier discussion gave assumptions a home. Writing them down as nodes converts "conflict with something never stated" into "conflict with a stated assumption" — a class the machinery can actually check.

1.3Canonical form — free prose in, comparable statement alongside

Authors keep writing freely; that is the point of SDD. But two atoms can only be compared, matched across releases (U5) or checked for conflict (U2) if they are written in a comparable shape. So each atom carries a canonical form produced by the agent and confirmed by the author — never typed by the author.

A good template already exists: EARS, the Easy Approach to Requirements Syntax (to verify), which reduces most requirements to a handful of patterns built around an optional state, an optional trigger, a subject and a response. Combined with the RFC 2119 modal vocabulary (to verify), it gives:

[While <state>] [When <trigger> | If <unwanted condition>] [Where <feature/scope>]
the <subject> MUST | MUST NOT | SHOULD | MAY <response>

# stored as fields, not only as a sentence
subject:    term:share_link          # resolved against the term registry
modality:   MUST
response:   "respond 404 Not Found"
trigger:    "an expired share link is requested"
state:      —
scope:      —
quantities: []                        # e.g. {value: 5, unit: GiB} normalized by code
  • The source text stays authoritative. The canonical form is a derived view with agent provenance. If they disagree, the source wins and the canonical form is re-derived.
  • Quantities are normalized by code, not by the agent. "5 gigabytes", "5GB", "5120 MB" are parsed and converted deterministically, so a comparison never depends on the model doing arithmetic.
  • Discussion 1's tuple (entity, property, constraint, condition) is a subset of these fields. The additions — modality, trigger vs. state, scope — are what distinguish "must" from "may" and "when" from "while", which is where many real conflicts hide.

1.4Deterministic guards around a non-deterministic atomizer

This is where O1 earns its keep. The agent's split cannot be proven right, but many ways of being wrong are mechanically detectable.

GuardWhat code checksCatches
G1 · Pre-segmentationMarkdown structure: headings, list items, numbered criteria become block boundaries before the agent sees anythingAtoms spanning unrelated sections
G2 · Span anchoringThe agent returns verbatim quotes; code finds each quote in the source and computes offsets. A quote not found verbatim is rejected. Offsets are never taken from the model.Paraphrase passed off as source; hallucinated text
G3 · CoverageEvery sentence carrying a modal verb ("must", "shall", "should", "never"…) is covered by some atom or explicitly labelled non-normativeSilently dropped requirements
G4 · No injectionEvery term and every quantity in the canonical form must appear in the atom's span (directly or as a registered alias). Otherwise the atom is marked inferred and needs explicit author acceptance.The agent adding "best practice" requirements nobody wrote
G5 · SchemaAnswer validates against the versioned JSON schemaMalformed output
G6 · Weak-word lexiconA configurable list ("fast", "appropriate", "user-friendly", "as needed", "etc.") flags candidate ambiguity — the idea is known in the literature as requirements smells (to verify)Vagueness the agent did not flag
What the guards cannot catch

A split that is well-anchored, fully covered and injection-free can still be semantically wrong — e.g. merging two obligations that T2 should have separated. That residue is what the author's confirmation at the button is for. The guards shrink what the author must look at; they do not remove the author.

1.5Ambiguity is a status, not a conversation (first release)

Per vision.md §3, the first release asks no clarifying questions. An ambiguous atom is still created, placed and linked, with check_status: ambiguous and a typed reason:

Ambiguity kindExampleDetectable by code?
vague term"uploads must be fast"Partly — G6 lexicon
unbounded quantity"large files", "many users"Partly — quantity missing where a comparative adjective appears
missing actor"files can be deleted"Partly — passive voice with no agent
referential"it retries three times" — which "it"?No — agent
scope"all users except guests on free plans" — (guests) on free plans, or guests (on free plans)?No — agent
unresolved termsubject names no registered term and no new term was confirmedYes — registry lookup

1.6Identity — the property U5 quietly depends on

If editing one paragraph re-atomizes the whole document, every node gets a new identity and every comparison becomes noise. So:

  • A node's id is assigned once and never recomputed from content.
  • When a source block changes (its hash changes), only that block is re-atomized. New atoms are aligned to old ones by span overlap, then by canonical-form match: unchanged edited split merged new removed. The author confirms the alignment.
  • Atomizer stability is a measured property: run the atomizer twice on the same block (without the lock) and record agreement. If it is low, T1–T4 or the prompt need work — that is a finding, not a failure to hide.

Check your understanding

  1. "Guests may view but not download shared files." Apply T1–T4. How many atoms, and what is the modality of each?
  2. Why does G2 require verbatim quotes instead of asking the agent for character offsets?
  3. An atom says "Files are encrypted at rest using AES-256" but the source only says "files are encrypted at rest". Which guard fires, and what status does the atom get?
PART 2

Place: layers, families — and why they are different axes

A layer says what kind of claim a node is. A family says what it is about. Conflating the two is the most common way spec graphs become unusable.

2.1What are layers actually for?

Three jobs were attributed to layers in the earlier discussions. Only two of them hold up:

JobVerdictReason
Human orientation — "where does this sit, what does it refine?"holdsPeople review specs by altitude.
Code generation — decompose and order work (U7)holdsContracts and data shapes must exist before the logic that uses them.
Blocking — only compare nodes within a layerweakThe costly conflicts cross layers: a storage choice (L2) against a throughput target (C). And a corpus of acceptance criteria sits almost entirely in one or two layers, so a layer fence skips almost nothing.
Fresh · differs from discussion 2

Discussion 2 made the layer "the blocking key". Here the layer is a kind, used for orientation and ordering; candidate generation for comparisons uses terms, families and edges instead (§2.8).

2.2The layer set, reconsidered

LayerThe claim is about…Verified by
L0 · IntentWhy the system exists; the outcome it servesBusiness outcome or stakeholder judgment — not by testing software
L1 · BehaviorWhat is observable at the system boundaryBlack-box test
L2 · StructureWhich components exist, what each owns, where they runInspection of structure / deployment
L3 · ContractThe agreement between two named parties: API, event, message, file formatContract test at that boundary
L4 · DataShape, type, identity, lifecycle of data — independent of who handles itSchema / data inspection
L5 · LogicInternal rules and algorithms of one componentWhite-box test
C · ConstraintsRules that quantify over many nodes: non-functional budgets, invariants, policiesA check applied across every node in its scope

Two things are deliberately not layers:

  • Verification (V) — a test spec is a node kind connected by a verifies edge to what it checks. It checks L1 and L5 and L3 alike; it refines none of them. fresh Discussion 2 kept L6 as a layer "for the visual"; removing it removes the temptation to draw a refinement edge from L5 to L6.
  • Terms (T) — the vocabulary plane: actors, entities, components, data types. Every node points into it. It is the backbone of families and retrieval (§2.5), and it had no home in either earlier design.

2.3The placement procedure — ask the verifier, not the vocabulary

Keyword rules ("contains POST → L3") are brittle, and asking an agent "which layer is this?" produces answers that cannot be audited. The proposal instead asks the agent a fixed, ordered questionnaire of yes/no questions, each answer backed by a quote. The compiler maps the answers to a layer with a fixed rule.

Q1  Does it restrict MANY nodes or the whole system, rather than
    describe one behaviour?                                      yes → C
Q2  Can it only be judged by a business outcome, not by testing?  yes → L0
Q3  Can an outside observer verify it WITHOUT naming a protocol
    artefact (path, method, status code, field, event)?          yes → L1
Q4  Is it about which component exists, owns, or runs something? yes → L2
Q5  Is it about an agreement between two named parties?          yes → L3
Q6  Is it about data shape/type/identity/lifecycle?              yes → L4
Q7  Is it an internal rule verifiable only white-box?            yes → L5

# all seven are asked, every time. mapping rule (code):
#  1. precedence  : the FIRST yes (Q1 → Q7) gives the layer
#  2. same claim  : a later yes whose quote OVERLAPS an earlier yes quote is ignored
#  3. two claims  : a later yes with a NON-overlapping quote on another layer → T3 fails → split
#  4. all no      : ambiguous (unplaceable) → author

Rules 2 and 3 explain how a node ends up in one layer and not the others. Many statements can honestly be read two ways: "a share link expires after 30 days" is observable behaviour and a data lifecycle. When both yes answers rest on the same words, it is one claim with two readings, and precedence decides. When the second yes rests on different words, the sentence is carrying a second claim, and it has to be split. Part 6 walks through this on real examples.

AtomFirst yesLayer
"Teams can share files with external partners."Q2 no · Q3 yesL1
"Reduce support tickets about lost files."Q2 yesL0
"FileService owns all file operations."Q4 yesL2
"POST /files returns 201 with the file id."Q3 no (names a method, path and status code) · Q5 yesL3
"A share link has an expiry timestamp."Q6 yesL4
"Every endpoint must respond within 300 ms."Q1 yesC
Caveat · the L1 / L3 overlap is real, and Q3's wording absorbs it

An API response is both externally observable (L1) and a contract (L3). Instead of a separate tie rule, Q3 is worded so that it excludes protocol artefacts. A statement that names a path, method, status code, field or event name answers Q3 "no" and lands in L3. A statement describing the effect a person or external party experiences stays in L1. Expect more tie cases to emerge from real corpora. Each fix is a versioned change to the question wording or the mapping, and past answers stay recorded.

P-8 · Why a questionnaire
  • Auditable — the recorded answers are the explanation.
  • Cheap to change — if layer definitions change, re-run the mapping over locked answers; nothing is re-asked.
  • Self-checking — contradictory answers expose non-atomic input (T3).
  • Hypothesis, not fact: that small closed questions are more stable than one open question is plausible, and must be measured on a real corpus.

2.4How generic can layers be? (U1)

A generic tool is tempted to let each project define its own layers. Resist it: two graphs built with different layer semantics cannot be compared (U5), and every downstream recipe (§3.4) would need per-project rewriting.

P-7 · Fixed semantics, configurable surface

The layer meanings are fixed by the compiler. A project profile may: rename layers for display; leave layers empty; and give hints — "sections titled Acceptance criteria are usually L1". Hints are priors recorded with the answer; they never override a questionnaire answer.

2.5Terms — the backbone nobody drew

Families, conflict candidates, retrieval and U5 matching all depend on one question: are these two nodes talking about the same thing? Text similarity answers a different question — "do these read alike?" — so the graph needs an explicit vocabulary.

term:
  id:        term:share_link
  canonical: "share link"
  aliases:   ["shared link", "public link", "download link"]
  kind:      entity | actor | component | data | external_system | event
  defined_by: node or definition span, if any
  • The agent tags each atom's subject and other referenced terms, proposing either an existing term or a new one.
  • The compiler resolves exact names and registered aliases deterministically.
  • A proposed alias merge ("download link" = "share link"?) always goes to the author.
The asymmetry that justifies author confirmation

A wrong merge of two terms fabricates conflicts between unrelated features. A wrong split of one term into two hides real conflicts. The first is noisy; the second is silent — and silent is worse. When in doubt the compiler should propose a merge for review rather than quietly keep the terms apart.

2.6Families — a vertical slice, not a similarity cluster

A family is everything about one subject, across all layers: the intent, behaviors, contracts, data, logic and constraints concerning share links. It is a vertical slice through the layer stack.

  • Why vertical: code is written per capability and reviewed per capability. A horizontal "similar text" cluster puts upload size limit next to download rate limit because they read alike, and separates share link expiry (L1) from the expiry timestamp field (L4), which must be built together.
  • How derived (deterministic): each node has exactly one primary term, chosen by a fixed rule. If the canonical subject is an entity, that entity is the primary term. If the subject is an actor, a component or "the system", the primary term is the first entity in the response. A test node takes the family of what it verifies, and a constraint takes the family its scope selects. The family name is the term name, with no naming call to a model.
  • Actors and components never seed a family. Otherwise "user" or "the service" would swallow half the graph. Components get their own coordinate (§2.7).
  • Mentioning is not membership. "When a file is deleted, its share links stop working" mentions files, but the obligation falls on share links. It joins the share-link family and gets a uses_term link to file, which retrieval can still follow.
  • Not by embeddings: similarity is the wrong question (above). In later releases a pinned local embedding model may suggest alias merges. It still would not assign families.
  • Overrides allowed, recorded: an author may pin a node to a family; the pin is stored and shown, so derived and hand-made grouping never mix silently. Hand-maintained family lists as the primary mechanism are rejected — they rot.
Fresh · differs from discussion 1

Discussion 1 formed families by entity match plus embedding threshold, and named new families with an LLM call. Its own example then hesitated over whether "download" belonged to "File Sharing" at a similarity of 0.62. With families seeded from the term registry, that question becomes: is the subject term the same, or an alias? — a registry lookup, and a merge proposal if unsure.

2.7A node's address has three coordinates

CoordinateAnswersComes from

The component coordinate matters most for U7: code is organised by component, specs by family, reviews by layer. A graph that records all three can be sliced whichever way the task needs.

2.8Placement is not linking

An address tells you where a node sits. Edges tell you what it touches. Retrieval (Part 3), conflict detection (U2) and comparison (U5) all run on edges.

EdgeFrom → toProduced by
uses_termnode → termAgent tag, compiler resolution
refineslower-layer node → higher-layer node it detailsAgent judgment on candidates
allocated_toL1/L3/L4/L5 node → component termAgent judgment; explicit when an L2 node names the owner

Candidate generation is deterministic: the compiler proposes which pairs the agent should judge — same term, same family, a constraint whose scope covers the node, refinement neighbours. The agent judges only those. Whether this candidate set contains the true relations is the single most important measured risk of the whole design, because a pair never proposed is a relation never found.

PART 3

Retrieve: the agent asks the graph, it never reads it

Designed now so the first release stores what U7 will need. The mechanism itself ships later.

3.1The principle

An agent reading a markdown spec set has one tool: search for words. Words find mentions, not relations — grep cannot answer "which constraints apply to this component?" or "what else breaks if this contract changes?". The graph's value to an agent is exactly that it can answer relational questions directly.

P-10 · Query, don't read

The compiler exposes a small, fixed vocabulary of deterministic queries through the agent integration (O3): node, neighbors(type, depth), family, component, layer, impact(node), context_pack(recipe, target, budget). The agent's context grows with the task, not with the size of the graph.

3.2Indexes — all deterministic

  • By id, term (including aliases), family, layer, component, status, source file/span. Plain inverted indexes; rebuilt from the graph.
  • Adjacency per edge type, in both directions — "what refines X" and "what does X refine" are equally common questions.
  • Optional lexical search over canonical forms, for when the agent has only a phrase.
  • Embeddings: optional recall aid only. If used, the model id is recorded and results are suggestions, never edges. Nothing the graph asserts may depend on them.

3.3Progressive disclosure — maps before territory

LevelWhat the agent seesSize depends on
0 · Project mapFamilies × layers counts; one line per family; open conflicts and ambiguities countNumber of families
1 · Family cardNode ids and one-line titles; contracts; constraints in scope; component allocationSize of one family
2 · NodeCanonical form, status, edges, annotationsOne node
3 · SourceThe exact source span and surrounding sectionOne passage

Family one-line summaries are agent judgments, so they go in the judgment lock, keyed by the hash of the family's member nodes. When a member changes, the summary is stale — the make rule, applied to summaries. The idea of hierarchical summaries over a corpus appears in recent retrieval work such as GraphRAG and RAPTOR (both to verify); the difference here is that the hierarchy is given by families and layers, not discovered by clustering.

3.4Context recipes — a traversal, not a search

For each kind of coding task, a recipe states which edges to follow and what to include. Recipes are code: the same graph and the same target always give the same pack.

Other recipes follow the same pattern with different edges:

  • change node N — N; everything that refines, verifies or depends_on N, transitively; the components those are allocated to.
  • review conflict — the two nodes; their sources; their refinement ancestors; constraints covering either.
  • compare to as-built (U5) — one family on both graphs, aligned by address.

3.5Budgets and declared omissions

A pack must fit a context budget. The cut rule is deterministic: tiers in priority order (core → contracts → constraints → data → verification → orientation), within a tier by edge distance then id; a node is never truncated mid-text. The essential part is the manifest: every node the recipe reached is listed as included, cut for budget, or flagged. An agent that knows its context is partial behaves differently from one that believes it is complete.

3.6Trace-back links — free now, valuable later

If generated code and tests carry the node ids they implement (a comment convention, a test-name convention), then later U3 (agent reports), U5 (as-built comparison) and impact analysis can cross the spec–code boundary without guessing. The first release only needs to define the id format and convention; nothing has to consume it yet.

3.7Honest limits

  • Missing edge = missing context, silently. A recipe cannot follow a relation nobody recorded. Mitigation: the manifest also lists nodes in the same family that the recipe did not reach, so gaps are visible.
  • Small spec sets may not need any of this. A project with a few dozen specs can put everything in context. Where the crossover lies is a question to measure, not a number to assume — and discussion 1's crossover figures were invented.
  • The fair baseline is not "one prompt with the whole markdown". It is a capable agent that can grep and plan over markdown. U7's value has to be shown against that.

4.1M6 in detail — comparing pre-built and as-built graphs

U5 compares a spec graph written before building with one written (by another agent or a human) after. The trap: if the two sides were atomized, named or placed differently, the diff reports method differences as system differences.

P-11 · Same compiler, same registry, both sides
  • Both graphs are compiled with the same atomization rules, question schemas and layer mapping version, recorded in each graph's header.
  • Both resolve against the same term registry; terms new on the as-built side enter as proposals, not silently.
  • Matching order: trace link (§3.6) if present → address (family, layer, component) → canonical form fields → agent judgment on what remains.
OutcomeMeaning
matched · equalBuilt as specified
matched · divergedSame claim, different value or condition — e.g. 30 days specified, 7 days built
matched · contradictedBuilt behaviour contradicts the design
pre-built onlySpecified, not (yet) built
as-built onlyBuilt behaviour nobody specified — often the most valuable finding
Granularity mismatch

Specs written from code tend to be finer-grained than design specs ("returns 413 when the body exceeds 100 MB" vs. "large uploads are rejected"). Matching must allow one-to-many, which is exactly the refines relation — so the comparison is really "does the as-built graph refine the pre-built one?". This is an open design question, not solved here.

5.2Open questions

  1. Do ambiguous nodes take part in conflict judgment, or wait until resolved? (Participating finds more; waiting avoids verdicts on unclear text.)
  2. Where are architecture decisions and their rejected alternatives recorded — L2 nodes with rationale annotations, or a separate decision kind?
  3. Tie rules for the questionnaire beyond L1 / L3 — collect from a real corpus before fixing.
  4. The pair-judgment question itself: which relation kinds, what schema, and how candidate completeness is measured (M1).
  5. Storage layout (M13) and graph file format.
  6. Which Claude Code integration carries which step — hook for the button, MCP tools for queries, headless invocation for batch? (vision.md §4)
  7. U5 granularity mismatch — is "as-built refines pre-built" the right comparison model?
  8. What the single writer must confirm at each press, and what may be auto-accepted (M9).

5.3Rejected in this file

  • Keyword rules as the layer classifier. Brittle; kept at most as project-profile hints.
  • Layer as the blocking key. Misses cross-layer conflicts and degenerates on single-layer corpora.
  • Embedding similarity deciding families or links. It answers "reads alike", not "about the same thing". In later releases it may act as a pinned, locked suggestion source.
  • LLM-named families. The term already is the name.
  • Per-project layer definitions. Breaks comparability (U5) and recipes (U7).
  • Offsets supplied by the model. Code computes them from verbatim quotes.

PART 6

Worked example: one small spec file, all the way through

Twenty-three lines of prose become fourteen nodes. For each one we trace why it lands in one layer and one family and not the others, then how indexes, progressive disclosure and a context recipe let an agent use the result. The same example, in compact form, is the test fixture in core-working-principle.md §9.

6.2Why a node lands in this layer and not another

The agent answers all seven questions for every node. The compiler applies precedence, then the overlap rule. What matters is less the yes that places a node than the other yes answers, and why they don't move it.

N-2 · "A share link expires 30 days after it is created."

QuestionAnswer · quoteWhat the compiler does
Q1 restricts many nodes?noIt concerns one entity's behaviour
Q2 business outcome only?noYou can test it
Q3 outside observer, no protocol artefact?yes · "expires 30 days after it is created"First yes → L1
Q6 data lifecycle?yes · "expires 30 days after it is created"Same words as the Q3 quote → one claim, two readings → ignored
Q7 internal algorithm?noIt describes an outcome, not how it is computed

Why not L4: the only L4 reading rests on the same words as the L1 reading, and L1 has precedence. That precedence is deliberate: if the outside world can see it, the code must honour it at the boundary. Why not L5: the algorithm lives on line 17 (N-12), which refines N-2. Now suppose line 5 had said "expires, computed as created_at + 30 days". Q7 would get a yes backed by different words ("computed as created_at + 30 days"). That is a second claim, so the compiler sends the atom back to be split into N-2 plus an L5 node.

N-10 · "…and 404 when it is expired or unknown."

Q3 says no: the statement names a status code on a path, which is a protocol artefact. Q5 says yes, because it is the agreement between the client and the service at GET /s/{token}. So it lands in L3. Why not L1: the observable effect a visitor experiences is already N-3 (line 6). N-10 is the contract that realizes it, so the graph records N-10 refines N-3 instead of filing two L1 nodes that say nearly the same thing.

N-4 · "Share links must never reveal the owner's email address."

Q1 says yes, quote "must never reveal": it restricts every page and response that involves a share link. Q3 also says yes, quote "never reveal the owner's email address". That quote overlaps the Q1 quote, so it is the same claim, and precedence places N-4 in C. Why not L1: as one L1 behaviour, it would reach code only where someone happened to link it. As C, its scope family:share_link guarantees that every recipe touching share links includes it (§6.6, tier 3).

N-11 · "A share link record stores token, file_id, created_at and expires_at."

Q3 no, because no outside observer sees stored fields. Q4 no, because "record" is data, not a component. Q6 yes. So it is L4, and nothing else is a candidate.

The one-line rule

A node is a member of exactly one family and mentions any number of terms. A family card shows its members. It also shows, separately, the nodes elsewhere that mention it. Nothing is lost, and nothing is filed twice.

6.4Indexes — the back-of-the-book idea

An index is what a textbook has at the back: instead of reading every page to find "expiry", you look up the word and jump to the page numbers. The compiler builds several such lookups from the graph. None of them involves a model.

by_family   share_link → N-1 N-2 N-3 N-4 N-5 N-7 N-9 N-10 N-11 N-12 N-13
            file       → N-6 N-8
            (global)   → N-14
by_term     file       → N-1 N-5 N-6 N-8 N-9
by_layer    L1 → N-1 N-2 N-3 N-5 N-6     L3 → N-9 N-10     C → N-4 N-14
by_component LinkService → N-1 N-2 N-3 N-5 N-7 N-9 N-10 N-11 N-12
edges_in    N-2 → refined by N-12 · verified by N-13

Two lookups, two different questions. by_family[file] answers "what is about files?" with N-6 and N-8. by_term[file] answers "what mentions files?" with five nodes. The three extra, N-1, N-5 and N-9, are exactly the share-link nodes an agent should glance at before changing how files work. Grep over the Markdown finds the word "file" in far more places, and cannot tell a member from a mention.

A question grep cannot answer: "If I change the 30-day expiry, what else changes?" edges_in[N-2] answers in one lookup: the algorithm N-12 and the test N-13. Nobody wrote "see also line 17 and line 20" in the prose. The links exist because placement and linking made them.

6.5Progressive disclosure — zooming in only where needed

Think of a map application: the country first, then a city, then a street, then a single building. An agent does the same with four levels, and at each level decides whether it needs to zoom further.

6.6A context recipe — "implement LinkService", tier by tier

A recipe is like a pre-written shopping list for one dish. Every time you cook it, you walk the same aisles in the same order. The graph is the store, and the recipe says which links to follow.

The point of the manifest

With the smaller pack, the agent knows that it has the record shape and the test only as titles, and that the file-deletion dependency was cut. It can ask node(N-11) for the fields. An agent that knows its context is partial asks. An agent that believes it is complete guesses.
